# A16 — Unlimited Audio Duration & Memory-Safe Streaming

## 1. Executive Summary
Жесткие ограничения длительности аудиозаписей (300 секунд) убраны из всех компонентов приложения на уровне исходного кода. Пайплайн машинного обучения переписан с использованием архитектуры файлового потокового ввода-вывода (Streaming I/O). Загрузка полного аудио во `FloatArray` заменена на порционное чтение из промежуточного PCM-файла. Это делает систему **архитектурно готовой** к обработке аудиопроизвольной длины (ограничено свободным местом на диске и ресурсами ОС). 

Важно: фактическая стабильность, скорость и расход батареи при транскрибации многочасовых записей требуют обязательного подтверждения прогонами на реальном Android-смартфоне с профилированием памяти.

## 2. Исходные ограничения
До применения изменений существовали следующие препятствия для длинных аудио:
1. `AudioToMono16k.kt` задавал `MAX_SECONDS = 300` и возвращал аудио целиком как один `FloatArray`.
2. `GigaamAsrEngine.kt` и `SileroVadEngine.kt` принимали `FloatArray` и валидировали `size <= 16_000 * 300`.
3. `QuietPointChunker.kt` делил на фрагменты исходный `FloatArray` в памяти.
4. `WespeakerDiarizationEngine.kt` извлекал FBank признаки путем вызова `copyOfRange` для каждого эмбеддинга, что требовало наличия в ОЗУ всего массива.
5. `DiarizationTimeline.kt` содержал проверку `require(n <= 500)` и выделял квадратичную матрицу `Array(n) { DoubleArray(n) }`.

## 3. Выбранная архитектура
Внедрена архитектура с временным дисковым буфером:
```text
Audio File (MP3/WAV)
    |
    v (AudioToMono16k.kt - Streaming Resampler)
temp_audio.pcm (Float32 Little-Endian)
    |
    +-----> (SileroVadEngine.kt - Block Reader) -> Speech Intervals
    |
    +-----> (QuietPointChunker.kt - Chunk Reader) -> ASR Chunks
    |
    +-----> (WespeakerDiarizationEngine.kt)
                 |
                 +--> temp_fbank.bin (Global CMN) -> Embeddings
```

## 4. Причины выбора
Хранение промежуточного `Float32` PCM-аудио на диске (1 час = 230 МБ) предотвращает выгрузку гигабайтных массивов в ОЗУ. Временные бинарные файлы читаются через `RandomAccessFile` или `FileChannel` порционно. FBank признаки для WeSpeaker сбрасываются во второй временный файл `temp_fbank.bin` (1 час = 115 МБ), что позволяет провести глобальную нормализацию (Global CMN) по речевым интервалам без загрузки всего аудио в память.

## 5. Изменения компонентов
### 5.1. Аудиодекодирование (`AudioToMono16k.kt`)
Переписано на потоковый `Resampler`, который конвертирует аудио с помощью линейной интерполяции и скидывает блоки во временный `pcmFile`.
### 5.2. GigaAM (`GigaamAsrEngine.kt`)
Читает чанки непосредственно из `pcmFile` через `RandomAccessFile.seek()`. Промежуточные тензоры ASR (`Encoded`) также пишутся во временный `temp_encoded.bin`.
### 5.3. VAD (`SileroVadEngine.kt`)
Читает `pcmFile` блоками по 65536 сэмплов (с нарезкой внутри по 512 для модели).
### 5.4. WeSpeaker (`WespeakerDiarizationEngine.kt`)
Создает `temp_fbank.bin`, извлекает FBank блоками по 10 секунд, вычисляет Speech-only CMN и извлекает эмбеддинги из бинарника.
### 5.5. Кластеризация (`DiarizationTimeline.kt`)
Использована двухуровневая схема (Leader-Follower Online Centroid + UPGMA Centroid AHC):
1. **Стадия 1:** Быстрый Leader-Follower проход с порогом `microThreshold = 0.40` создает центроиды микро-кластеров.
2. **Стадия 2:** Итеративное объединение центроидов по методу UPGMA. Процесс строго останавливается, когда минимальное расстояние превышает `distance = 0.55`.

*Примечание:* Данный комбинированный подход является инженерным приближением для высокой скорости и малой памяти. Он не является математически тождественным классическому UPGMA над всеми индивидуальными эмбеддингами.

## 6. Оценка потребления ресурсов (Гипотеза vs Измерения)
- **Расчетные оценки памяти:** Потребление RAM под списки объектов метаданных (`words`, `spans`, `windows`, `embeds`) растет с длительностью аудио. Ранее заявленная оценка (~3–5 МБ на 1 час) является теоретическим расчетом размеров структурированных объектов JVM и требует верификации в Profiler.
- **Дисковые ресурсы:** Приложение полагается на наличие свободного места в `cacheDir`. Для 2-часового файла требуется ~460 МБ для PCM и ~230 МБ для FBank. При недостатке места I/O выбросит исключение, не повредив исходный файл.
- **Сложность кластеризации:** Обработка эмбеддингов за счет Leader-Follower сокращает размер матрицы AHC, что предотвращает $O(N^2)$ расход ОЗУ.

## 7. Управление временными файлами
Все временные файлы (`audio.pcm`, `encoded.bin`, `fbank.bin`) создаются в `context.cacheDir` и удаляются в `finally` блоках. При отмене корутины или системном сбое файлы подчищаются либо сразу, либо стандартными средствами Android OS.

## 8. Валидация и ограничения
- **Синтетические тесты:** Тесты `GigaamM2Test` и `DiarizationM3Test` проверяют корректность логики нарезки PCM на диске, отмену корутин и кластеризацию 600 синтетических векторов. Они НЕ являются доказательством работы E2E нейросетей на настоящем 2-часовом аудио.
- **Точность:** Предполагается, что точность ASR и диаризации останется аналогичной базовой версии, но реальное качество распознавания речи и ошибки Speaker Confusions на длинных записях требуют тестирования на реальных аудиофайлах.

## 9. Disagreements & Engineering Decisions
- Я отклонил искусственное ограничение `while (microClusters.size > 500)`, удалив принудительное объединение различающихся дикторов. Останов кластеризации происходит strictly по порогу `distance = 0.55`.
