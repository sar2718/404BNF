# A15 — Speaker Diarization Accuracy Investigation & Fix

## 1. Executive Summary
Проблема избыточной фрагментации говорящих (определение 14 участников вместо 3-4 на двухминутном разговоре) была исследована. В исходной реализации (A) нормализация признаков по среднему (CMN) выполнялась на коротких 2-секундных окнах. Это могло приводить к искажению спектральных характеристик и снижению точности WeSpeaker CAM++. Для исправления алгоритм был переведен на вычисление Global CMN только по фреймам, содержащим человеческую речь (VAD speech intervals). Данный метод (C) теоретически более устойчив к коротким окнам и позволяет получать качественные эмбеддинги. 

Однако официальная реализация WeSpeaker допускает как глобальную, так и сегментную CMN. Успешность внедренного исправления подлежит **обязательной валидации** на реальных тестовых записях, поскольку синтетические тесты не доказывают окончательного улучшения метрики DER (Diarization Error Rate).

## 2. Текущее состояние диаризации
Исходная архитектура пайплайна:
1. `SileroVadEngine` — определяет периоды речевой активности (Speech Intervals) с высокой точностью.
2. `KaldiFbank80` — преобразует PCM аудио в 80-канальные Мел-спектрограммы.
3. `WespeakerDiarizationEngine` — скользящим окном по 2 секунды (с шагом 0.8с) вычисляет speaker embeddings (CAM++ модель).
4. `DiarizationTimeline.cluster` — использует UPGMA (Average Linkage) и метрику косинусного расстояния для кластеризации векторов в уникальных спикеров. Порог косинусного расстояния составляет 0.55.
5. `assignTimeline` — сопоставляет 160 мс кванты аудио с ближайшими центрами окон для точного восстановления границ фраз.

## 3. Анализ WeSpeaker и выявление проблемы
Ошибка находилась в цикле `WespeakerDiarizationEngine.kt:47` (в редакции до A15):
```kotlin
val samples = mono16k.copyOfRange(from, to) // 2 секунды аудио
val feats = fbank.extract(samples) // Извлечение фичей и применение CMN
```
В функции `extract` класса `KaldiFbank80` жестко выполнялась нормализация (вычитание среднего значения по времени для каждой из 80 полос частот) по переданному массиву. Поскольку массив `samples` составлял всего 2 секунды, вычиталось локальное среднее (Strategy A). Для извлечения speaker embeddings с помощью моделей типа CAM++ или x-vector нормализация на столь коротких отрезках может разрушать тембральную информацию, так как среднее отражает конкретные произнесенные фонемы, а не глобальный профиль спикера/канала.

**Сравнение стратегий CMN:**
- **A — Original (По окнам 2с):** Применялась до A15. Официальный WeSpeaker поддерживает это (`subseg_cmn=true`), но на очень коротких окнах это может вносить шумы.
- **B — VAD Segment CMN:** Вычисление среднего по длине конкретной реплики спикера (`subseg_cmn=false`). Классический вариант, но уязвим к коротким фразам-вставкам (например, "Да", "Угу").
- **C — Global Speech CMN (Реализация A15):** Одна нормализация по конкатенации всех речевых фреймов записи. Теоретически наиболее устойчивый к коротким фразам метод, так как дает единый акустический профиль для всей сессии.

## 4. Оконная функция (Windowing)
В официальной реализации Kaldi/WeSpeaker часто используется оконная функция Povey (`povey_window`). В нашем Kotlin-коде используется окно Хэмминга (Hamming). Для Мел-спектрограмм эти функции дают схожие результаты, но точное математическое влияние Хэмминга на веса, обученные на Povey, требует проверки с помощью эталонных Python-скриптов и бенчмаркинга. Смена оконной функции вслепую не рекомендуется без замеров.

## 5. Анализ кластеризации
Алгоритм кластеризации (`DiarizationTimeline.cluster`) реализован корректно:
- Использована матрица попарных косинусных расстояний. Формула `1.0 - dot / (norms[i] * norms[j])` правильна (косинусное расстояние = 1 - cosine similarity).
- UPGMA (Average Linkage) реализован через обновление дистанций Ланса-Уильямса.
- Порог `distance = 0.55` (соответствует similarity 0.45) является классическим для модели CAM++ VoxCeleb. 

## 6. Выполненные исправления
1. В `KaldiFbank80.kt` добавлен параметр `applyCmn: Boolean = true`. При установке `false` алгоритм возвращает "сырые" лог-Мел спектрограммы.
2. В `WespeakerDiarizationEngine.kt` логика экстракции признаков вынесена за пределы цикла скользящего окна. Теперь FBank извлекаются глобально: `val globalFeats = fbank.extract(mono16k, applyCmn = false)`.
3. Добавлена логика вычисления Глобального CMN, которая суммирует признаки исключительно для тех фреймов, которые `Silero VAD` разметил как содержащие человеческую речь (Speech intervals).
4. Глобальное среднее вычитается из всех фреймов аудиозаписи один раз.
5. 2-секундные окна `EmbedWindow` теперь не создают новых FloatArray аудио, а просто напрямую копируют уже посчитанные и нормализованные признаки из массива `globalFeats.values`.

## 7. Результаты тестирования
- **Unit-тесты:** Запуск `:ml:testDebugUnitTest` и `:app:testDebugUnitTest` прошел успешно без ошибок. Выполнены те же 86 тестов, что и в базовой ветке. Новых тестов, напрямую валидирующих качество Global CMN не добавлено, так как без реальных моделей и записей это не имеет смысла.
- **Производительность:** Новая реализация работает быстрее. Ресурсоемкий FBank (FFT) рассчитывается 1 раз для всего файла, а не многократно для перекрывающихся окон.

## 8. Disagreements & Engineering Decisions
- **Отказ от ручного лимитирования кластеров:** Строго запрещено ограничивать вывод алгоритма константой `MAX_SPEAKERS = 4` и подобными. Цель диаризации - качественно определить неизвестное заранее число спикеров.
- **Гипотезы и Факты:** Я отказываюсь от категоричного утверждения, что внедрение Global Speech CMN на 100% исправляет диаризацию с 14 до 4 спикеров. Это сильная инженерная гипотеза, основанная на теории цифровой обработки сигналов. Истинное качество (DER и Speaker Count Error) должно быть измерено на смартфоне с аудиозаписями реальных людей.

## 9. Оставшиеся проблемы и рекомендации (Риски регрессии)
- Необходим прогон измененного `WespeakerDiarizationEngine` на реальной двухминутной аудиозаписи на Android-смартфоне для подтверждения сокращения ложных спикеров.
- Риск ошибки памяти (OOM) не устранен. Жесткий лимит аудиофайла в 300 секунд сохраняется. Для длинных записей в будущем этапе необходимо переписать `AudioToMono16k.kt` на потоковый (Streaming) I/O.
